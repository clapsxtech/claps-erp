# Front end: build, structure and asset security

The only front end is the React + Astryx app in `resources/app`. How screens, permissions and tests fit
together is described in [the app README](../resources/app/README.md).

## Build

```sh
npm ci
npm run production        # minified build into public/ui
npm run development       # readable build
npm run watch             # rebuild on change
npm test                  # type-check, build test, deployment tests
```

- **Build output:** `scripts/build-assets.mjs` runs esbuild with the StyleX plugin.
  - It writes hashed, code-split bundles to `public/ui`.
  - It writes `public/ui/manifest.json`, which the host page (`resources/views/app/shell.blade.php`) reads.
- **Styles:** Astryx ships prebuilt CSS. The StyleX plugin compiles only the app's own `stylex.create()` calls.
- **Theme:** the ClapsLearn theme was made with the Astryx theme editor.
  - Editor source is in `themes/claps`.
  - The copy the app imports is in `src/themes/claps`, regenerated by the editor.
  - The container build copies `src/themes` (see `Dockerfile.cloudflare` and `.dockerignore`).
- **Parallel builds:** `UI_OUT=public/ui-x` builds into another folder. Serve it with `APP_UI_DIR=ui-x`.

## Delivery

- **Cloudflare edge:** `scripts/stage-cloudflare-assets.mjs` copies only `public/ui`, `favicon.ico` and
  `robots.txt` into `.cloudflare-assets`. The Worker serves those files at the edge.
- **Laravel container:** every other request, including all pages, which return the host page.
- **What is never staged:** PHP, uploads, source maps, dotfiles and symlinks.
- **Dependencies:** all browser code is bundled from the locked npm dependencies. There are no CDN scripts.
  - The only exception is the error pages (`resources/views/errors/*`), which are self-contained and inline
    their CSS, so they still render if the JavaScript app is broken.

## Host page

- **One shell:** the host page renders for `/app/*`, `/print/*` and every portal page.
- **Session JSON:** it embeds a small JSON session in `<script type="application/json" id="erp-session">`.
  The session holds only what that visitor may see: the user, their teams, and per team the pages, actions
  and exports their role allows.
- **Server-enforced:** the session only decides what to show. Every JSON route is checked again on the server.

## Phones and tablets

The app is meant to be run from a phone, so every screen is built phone-first:

- **Breakpoints.** `useIsPhone()` (under 768px) switches to the phone shell: a bottom tab bar with the role's four main places plus "More" (the searchable list of everything). `useIsCompact()` (under 1024px, so portrait tablets too) switches lists to cards.
- **Lists and tables.** Registers use `DataTable`; on compact screens rows become cards, sorting becomes a "Sort" picker and CSV export stays available. Small fixed tables use `RowTable` (never Astryx `Table` directly): on compact screens each row is a card whose first column is the title, titled columns are label/value lines and untitled columns (row actions) sit underneath at full width. Printable documents (`pages/Print/*`, parent invoices and statements) keep real tables.
- **Tabs.** Use `ViewTabs`. A strip that would not fit the screen (worked out from the viewport width) becomes a full-width "View" picker, a bottom sheet on phones, so no view is hidden off screen.
- **Touch sizes.** `resources/app/touch.css` applies on touch screens only (`pointer: coarse`): controls, fields, list rows, menu and picker rows, nav items and sortable headers are at least 44px tall, and text fields use 16px text so iPhones do not zoom when one is tapped. Desktop density is unchanged.
- **Dates.** Astryx `DateInput` uses the phone's own date picker on touch screens; there is nothing to add.
- **Contact.** Phone numbers are `tel:` links; international numbers also get a WhatsApp link (`lib/contact.ts`).
- **Install.** `public/manifest.webmanifest` (staff and teachers, opens `/`) and `public/parent.webmanifest` (parents, opens `/parent`) with the icons in `public/icons` let people add the app to their home screen, where it opens full screen. There is no service worker: the app needs a connection, and nothing is cached offline.

To check a change on a phone, run the app and look at it at 360px wide with touch emulation (Chrome DevTools device mode, or Playwright with `isMobile: true, hasTouch: true`): nothing may scroll sideways and every control must be at least 44px tall, including inside open menus, pickers and drawers. Check 768px (portrait tablet beside the sidebar) and 1024px too.

## Writing for people

The app is used by teachers, sales staff and parents, not accountants. Screen text follows these rules:

- **Plain words for money.** `lib/plain.ts` holds the one wording for each money idea and translates the server's states: a class is *billed to the family* (not "imported for charge"), approved attendance is *added to the teacher's pay* (not "accrued"), and a *possible duplicate* is a class that may be recorded twice. Precise accounting terms stay on Accounts & tax only.
- **Say what to do next.** The staff home starts with a greeting and "Needs you today" in sentences ("3 classes are waiting for your approval"). Every empty state says why it is empty or what to do.
- **Errors say how to fix it.** Validation messages come from `resources/lang/en/validation.php` with plain field names ("Please fill in the joining date", "Please choose the student"). A dropped connection reads "Could not connect. Check your internet and try again", never "Failed to fetch".
- **Money disclaimers keep their meaning.** Screens still say that recording a payment takes or sends no money, in everyday words.
- **Warm, not bare.** Screens use colour and pictures to be read at a glance: figure tiles (`Metric`) carry an icon chosen from their label and a soft colour (amber when something waits, red when something is wrong, tinted when it is the selected list); people in lists show initials avatars (`phoneCard.avatar`); the staff, teacher and parent homes open with a green welcome card. The theme's greys are tinted with the brand green. Colours come from Card variants and the theme, never hand-written CSS.
